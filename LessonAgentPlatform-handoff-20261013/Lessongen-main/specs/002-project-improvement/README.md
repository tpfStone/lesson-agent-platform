## 本规格解决什么

把目前能够本地运行、但存在多份代码混用、启动不可复现、初稿可能绕过 Critic、测试和研究证据不足的问题，拆成可独立验证的改进切片。截图中的 P0→P3 是**优先级**，不是承诺所有能力都会进入下一次发布；每个阶段须通过退出门槛，再决定是否推进。

| 优先级 | 目的 | 完成标志 |
| --- | --- | --- |
| P0 工程基础 | 唯一代码来源、环境可复现、离线 CI、敏感信息与 Git 可控 | 新机器按文档启动 F 仓库；离线测试自动运行；不依赖 C 盘安装 |

| P2 能力演进 | 在基线和评估集之上试验 Critic 并发、权威资料检索、Paper#3 联动与模型配置 | 各能力有开关、失败降级和对照数据；不凭主观观感合并 |
| P3 研究与发布 | 人工评价、受控对照、隐私伦理、许可证及公开部署门槛 | 可复核证据与授权齐备，才讨论对外发布或教学成效 |

## 执行约束

- 现有 `web/specs/001-lesson-plan-web` 是已经实现的 MVP 历史规格，本规格是增量变更，不回填历史完成状态。
- C 盘旧工程已在用户授权下备份至 `F:\comalesson\archive\C_PR_full_20260923` 后清理；历史数据库和运行 artifacts 不因 P1 修改而删除。所有后续开发只在本 F 仓库进行。
- 所有新功能先保留可比较的旧行为开关与固定测试样例。真实模型结果有随机性，不能把某次 Judge 涨分当作教学效果。
- CI、文档和离线测试不得调用收费 API；真实调用必须经预算控制和人工触发。
- 对 Paper#3、RAG、人类受试者实验和公开发布，本规格只定义进入条件，不宣称目前已完成。

## 变更门槛

每个任务按“基线测试 → 契约/失败测试 → 最小实现 → 回归 → 记录证据 → 审核合并”完成。凡修改 JSON Schema、公开 API、停止原因或 artifacts 命名，必须同时更新对应契约、兼容策略和迁移说明。不得为了让测试变绿而降低既有安全校验或将失败伪装为成功。
